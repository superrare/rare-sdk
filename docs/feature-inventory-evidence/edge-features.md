## Gate evidence and uncertainties

`server/permissions/address-feature.ts` defines three address lists: `FEATURE_FLAG_ADMIN_ADDRESSES`, `COLLECTIONS_MINT_ADDRESSES_ARTIST`, `LIQUID_DEPLOY_ARTISTS`. `isLiquidEditionFeatureAddress` permits any of FeatureAdmin, CuratedCollectionArtist or LiquidEditionArtist. These are website product gates distinct from contract permissions; SDK wallet calls do not recreate them. No list contents or production configuration was examined.

Physical sell mode requires both physical flags at build time. This does not prove every existing physical detail/print checkout uses the same gate. Print fulfillment is configured per release and proves a mint receipt; chain numbers observed in tests (1 and 11155111) are not evidence of all live supported release chains.

No dedicated physical holder redemption action or Liquid fee claim action was located; mark these **unverified/uncertain**, not an SDK-only gap or confirmed live web capability. ABI function availability is insufficient evidence of a user-facing workflow.

Sales attribution looks like an admin tool by route/title, but the page and queried read routers inspected do not establish an authorization gate. Do not label it staff-only without checking enclosing layout/middleware and `baseProcedure`.

Browser media upload, metadata/indexing handoff, terms/disclaimer consent, private fulfillment state, Google Sheet example downloads, and spreadsheet export are independent action surfaces even when the underlying on-chain write has SDK parity.
